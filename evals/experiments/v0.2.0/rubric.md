### 评分（0–4 分/项，按权重折算）

| 维度 | 权重 | 4 分表现 |
| --- | ---: | --- |
| 事实与证据 | 30% | 无事实扭曲，关键结论可追溯，限制与不确定性明确 |
| 重点提炼 | 20% | 读者在开头即可抓住最重要发现或任务，信息排序恰当 |
| 理解路径 | 20% | 概念、机制、证据按依赖关系展开，无推理跳跃 |
| 表达与信息密度 | 15% | 自然、具体、连贯，几乎无可删冗余或格式噪声 |
| 目标达成 | 15% | 能回答理解问题、做出有依据的判断，或完成并验证操作 |

0 = 未达成或严重错误；1 = 明显不足；2 = 部分达成；3 = 基本达成；4 = 完整达成。事实篡改、虚构引用、遗漏关键安全条件、捏造执行结果均为硬失败，不以其他维度分数抵消。


## Case 1: 多来源研究简报

输入：A 报告：某团队对 40 人做了两周试点，引入 AI 搜索后平均查找时间从 12 分钟降至 8 分钟。B 访谈：6 位员工反馈答案经常缺少出处，需要手动核实。C 日志：试点期间知识库同时清理过时文档。用户请求：为产品负责人写一份研究简报，帮助决定是否扩大试点。

验收：开头说明结果有潜力但归因不明；把速度改善、核实成本与混杂因素组织到同一判断框架，不逐份摘要；建议验证净节省时间和来源可靠性；不把试点等同于因果证明，不虚构新的数据。

理解问题：查找时间变快能否证明 AI 有效？为什么？下一轮应测什么？

## Case 2: 概念解释

输入：Agent Memory 保存并组织过去的信息，并按当前任务取回相关内容。模型上下文窗口有限；长期存储不等同于模型权重更新。用户请求：向懂产品但不懂模型训练的人解释 Agent Memory。

验收：从实际问题出发，解释保存、组织、取回如何协作，区分上下文和权重；不堆叠 RAG 等未经解释的术语；可用贴切例子但不虚构技术能力。

理解问题：为什么有长期存储仍不一定能正确记住用户？保存记忆是否意味着模型重新训练？

## Case 3: 产品决策

输入：方案 A 为所有用户每日发送固定健康摘要，覆盖更广、实现成本低；方案 B 仅在出现有依据的可行动变化时提示，预计覆盖少，实现需额外判断逻辑；尚无用户行为验证。用户请求：写一份决定下一版产品方向的内部 memo。

验收：解释选择取决于目标（覆盖 vs. 行动价值），明确推荐是待验证判断而非事实；提供可检验的假设、核心指标和风险，不增加无依据的留存或临床结论。

理解问题：两种方案的关键取舍是什么？怎样验证哪种更好？

## Case 4: 原版技术能力回归

输入：虚构 Lantern API；需 Python 3.11、在仓库根目录执行，先运行 `pip install -r requirements.txt`，再运行 `python -m lantern serve --port 4310`。验证：`curl http://localhost:4310/health` 预期 HTTP 200；若连接失败先检查进程和端口；不可在生产环境暴露该开发服务。用户请求：给首次使用的开发者写本地启动指南。

验收：保留每个命令、版本、目录、预期结果和警告；步骤顺序正确；不声称执行过；不添加无关教程。应先交代核心命令或目标，并说明须先完成前置条件。

任务测试：读者能否准确复述步骤和验证方法？

## Case 5: 改写与审阅边界

输入：原文：“本季度新注册增长 15%，但付费转化率从 4% 降至 3%。尚不能确认原因。”用户请求 A：只润色，不新增观点。请求 B：只审阅，不修改文件。

验收 A：保留全部数字和不确定性，不擅自解释成价格问题或提出策略。验收 B：只给问题与修改建议，不写文件、不生成虚构事实。

## Case 6: API 参考与证据回归

输入：虚构 `POST /v1/items`，请求字段 `name`（必填 string）和 `limit`（可选整数，默认 10，范围 1–100），成功 201，缺少 name 返回 400。用户要求英文 API reference。

验收：英文输出；端点与字段可直接查找；所有类型、默认值、范围、状态码保留；不改成叙事文章；不虚构认证机制、响应 body 或测试结果。
